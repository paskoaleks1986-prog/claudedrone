# ClaudeDrone — Repository Architecture / Архитектура репозитория

> This document explains the repository structure: what goes where and **why**.
> Этот документ объясняет структуру репозитория: что где лежит и **почему**.

---

## 🧠 Core Design Decision / Главное архитектурное решение

ClaudeDrone is built on a single key idea:

> **The drone does not think. It only feels and moves.**

All intelligence — navigation, mapping, decision-making — runs on an **external computer** connected via WiFi.
The drone itself is just a platform: it reads sensors and executes movement commands.

This is called a **distributed compute architecture** — the brain and the body are physically separated.

**Why?**

| Problem | Solution |
|---|---|
| Computers powerful enough for SLAM are heavy | Run SLAM on external PC, keep drone light |
| Algorithms change often during research | Swap software on PC without touching drone hardware |
| Debugging crashes is easier on a PC | All logic is on a machine that won't fall from the sky |
| Power budget on a drone is tight | Heavy compute draws power that motors need |

**Аналогия для новичка:** представь, что дрон — это тело, а внешний компьютер — это мозг. Тело чувствует (сенсоры) и двигается (моторы), но все решения принимает мозг снаружи. Связь между ними — WiFi, как нервная система.

## 📂 Folder-by-Folder / Папка за папкой

### `firmware/` — Код для микроконтроллеров

**Firmware** (прошивка) — это код, который прошивается прямо в чип и работает на нём постоянно. В отличие от обычных программ, он запускается без операционной системы, прямо на железе.

#### `firmware/esp32/`

**Что здесь:** C++ код для ESP32, собирается через PlatformIO.

**Что делает ESP32 в нашем проекте:**
- управляет сервоприводом SG90 (вращает лидар для сканирования)
- читает дальномеры TF-Luna (по UART) и VL53L0X × 6 (по I2C через мультиплексор TCA9548A)
- читает оптический поток PMW3901 (скорость X/Y)
- общается с полётным контроллером по SBUS/MSP
- передаёт все данные на RPi Zero 2W

**Почему ESP32, а не сразу RPi?**
ESP32 — это микроконтроллер реального времени. Он реагирует на события за микросекунды и не "залагает". RPi — это мини-компьютер с Linux, где операционная система может задержать выполнение кода на миллисекунды. Для управления сервоприводом и чтения сенсоров каждые несколько миллисекунд нужна именно такая точность.

**Аналогия:** ESP32 — как рефлексы (дёрнуть рукой от огня). RPi — как сознательное мышление (решить, куда идти).

#### `firmware/fc/`

**Что здесь:** конфигурация полётного контроллера (F4/F7 FC).

Полётный контроллер — это специализированная плата, которая делает одно, но очень хорошо: удерживает дрон в воздухе. Она читает гироскоп и акселерометр сотни раз в секунду и корректирует обороты моторов, чтобы дрон не падал.

Мы не пишем код для FC — только конфигурируем его (через Betaflight/INAV).
Здесь хранятся: backup конфигов, CLI dump, PID-настройки.

### `software/` — Код для компьютеров (не чипов)

В отличие от firmware, это обычный Python-код, который работает на операционной системе.

#### `software/onboard/`

**Что здесь:** Python-код для **Raspberry Pi Zero 2W**, который находится на дроне.

RPi Zero 2W — это мини-компьютер с Linux на борту дрона. Его роль:
- собирать данные от ESP32 (по UART/Serial)
- упаковывать их и отправлять на внешний PC по WiFi (UDP/WebSocket)
- получать команды движения от внешнего PC и передавать на ESP32

RPi — это **WiFi-мост и агрегатор данных**. Он не принимает никаких решений по навигации.

**Аналогия:** RPi на борту — как позвоночник. Он передаёт сигналы от рецепторов (сенсоры) к мозгу (внешний PC) и обратно к мышцам (ESP32 → FC → моторы).

#### `software/compute/`

**Что здесь:** Python-код для **внешнего PC** (твой ноутбук/сервер).

Это главный мозг системы. Здесь работает:
- **SLAM** (Simultaneous Localization and Mapping) — алгоритм, который одновременно строит карту и определяет положение дрона на ней
- **Path planning** — планирование маршрута (A*, RRT)
- **Mission logic** — высокоуровневая логика миссии (куда лететь, что делать)

#### `software/sensors/`

**Что здесь:** Python-драйверы и утилиты для работы с сенсорами.

Переиспользуемый код для чтения TF-Luna, VL53L0X, PMW3901. Можно тестировать каждый сенсор отдельно, подключив его к PC через USB-UART адаптер — без запуска всей системы.

#### `software/llm/`

**Что здесь:** всё, что связано с использованием языковых моделей (LLM) в проекте.

**Зачем LLM в дроне?**
LLM выступает высокоуровневым планировщиком. Пример: вместо того чтобы вручную задавать координаты, ты говоришь *"облети периметр комнаты"* — LLM разбивает это на конкретные waypoints и команды для `compute/`. Это называется **task planning**.

**Что хранится:**
- `prompts/` — системные промпты для разных задач (навигация, интерпретация карты, планирование миссий)
- `config/` — YAML-конфиги моделей для **Ollama** (инструмент локального запуска LLM). Пример конфига:
  ```yaml
  model: llama3
  temperature: 0.2
  context_window: 8192
  ```
- `integration/` — скрипты, связывающие LLM с `compute/`: как модель получает карту и отдаёт команды

**Локально или через API?**
Для экспериментов — через API (Anthropic/OpenAI). Для автономной работы без интернета — локально через Ollama. Для локальных моделей желательна GPU (минимум RTX 3060 12GB для моделей 7B параметров).

#### `software/ros/`

**Что здесь:** ROS 2 пакеты для интеграции с роботизированной экосистемой.

**Что такое ROS?**
ROS (Robot Operating System) — это не операционная система, а **фреймворк-посредник** между модулями робота. Представь его как почтовую систему: каждый модуль (сенсоры, SLAM, навигация) — это отдельный **node** (узел), они общаются через **topics** (каналы публикации).

Пример цепочки в нашем проекте:
```
node: sensor_reader  →  topic: /scan
node: slam           →  topic: /map
node: planner        →  topic: /cmd_vel
```

**Важно:** ROS 2 слишком тяжёлый для RPi Zero 2W — работает только на внешнем PC. На дроне у нас свой лёгкий протокол.

**Что хранится:** определения пакетов (`package.xml`), launch-файлы, кастомные msg/srv типы сообщений, node-скрипты.

### `simulation/` — Симуляция

**Что здесь:** всё для запуска виртуального дрона в симуляторе **Gazebo**.

**Зачем симулятор?**
Тестировать алгоритмы на реальном дроне дорого и опасно — дрон может упасть. Gazebo — физический симулятор: можно смоделировать дрон, комнату, сенсоры и запустить SLAM или навигацию **не поднимая реальный дрон**. Алгоритм сначала работает в симуляторе, потом переносится на железо.

**Аналогия:** как авиасимулятор для пилотов — сначала тренируешься виртуально, потом садишься в настоящий самолёт.

#### `simulation/models/`
URDF/SDF модель дрона — описание его физической формы, массы, расположения сенсоров для симулятора.

**URDF** (Unified Robot Description Format) — XML-файл, который описывает робота: из каких частей состоит, как они соединены, где расположены сенсоры.

#### `simulation/worlds/`
SDF-файлы виртуальных комнат и сред для тестирования: пустая комната, коридор, комната с препятствиями.

#### `simulation/launch/`
Launch-файлы для быстрого запуска симуляции одной командой:
```bash
ros2 launch simulation indoor_room.launch.py
```

### `hardware/` — Физическое железо

#### `hardware/schematics/`

**Что здесь:** электрические схемы подключения всех компонентов.

Схемы хранятся в двух форматах:
- `.fzz` — исходники **Fritzing** (редактируемые схемы). Fritzing — визуальный редактор электрических схем, специально сделанный для таких проектов: можно рисовать подключения прямо на картинке макетной платы
- `.png` / `.svg` — экспортированные изображения для документации и README

**Зачем хранить в репо?** Чтобы любой человек мог собрать точно такой же дрон, не угадывая подключения.

#### `hardware/mounts/`

**Что здесь:** STL-файлы для 3D-печати креплений.

Сенсоры нельзя просто приклеить скотчем — нужны точные крепления. Особенно для TF-Luna на сервоприводе SG90: угол установки критичен для точности сканирования.

### `docs/` — Документация

| Файл / Папка | Содержимое |
|---|---|
| `architecture.md` | Этот файл — объясняет структуру репо и архитектурные решения |
| `roadmap.md` | Фазы проекта, прогресс, milestone'ы |
| `sensors.md` | Описание каждого сенсора: принцип работы, характеристики, подключение |
| `notes/` | Рабочий дневник: заметки по инструментам, наблюдения, эксперименты |

#### `docs/notes/`

Свободный формат — markdown-файлы с датой в названии или по теме. Примеры:
- `fritzing-getting-started.md` — первые шаги в Fritzing, полезные трюки
- `ros2-installation.md` — как ставил ROS 2, что пошло не так
- `tfluna-calibration.md` — наблюдения по калибровке TF-Luna
- `2024-01-15-first-scan.md` — дневниковая запись после первого успешного сканирования

**Зачем это в репо, а не в Notion/блоге?**
Заметки живут рядом с кодом и схемами — они версионируются вместе с проектом. Когда через полгода ты откроешь старый коммит, заметки объяснят, почему было принято то или иное решение.

## 🔄 Data Flow / Поток данных

```
[Физический мир]
      │
      ▼
[Сенсоры на дроне]
  TF-Luna, VL53L0X, PMW3901
      │ I2C / UART
      ▼
[ESP32]  ←── firmware/esp32/
  Чтение сенсоров, управление сервоприводом
      │ UART / Serial
      ▼
[RPi Zero 2W]  ←── software/onboard/
  Агрегация, упаковка данных
      │ WiFi (UDP/WebSocket)
      ▼
[Внешний PC]  ←── software/compute/ + software/ros/ + software/llm/
  SLAM, Path planning, Mission logic, LLM task planning
      │ WiFi (команды движения)
      ▼
[RPi Zero 2W] → [ESP32] → [FC] → [Моторы]

── Параллельно ──────────────────────────────────────
[simulation/]  ←── Gazebo + ROS 2
  Виртуальный дрон для тестирования алгоритмов
  без поднятия реального железа
```

## 🧩 Why This Structure Works / Почему такая структура работает

1. **Изолированность** — каждая папка — это независимый модуль. Можно тестировать сенсор, не запуская весь дрон.
2. **Заменяемость** — можно поменять алгоритм SLAM в `compute/`, не трогая firmware. Можно заменить LLM-модель в `llm/config/`, не меняя остальной код.
3. **Симуляция перед железом** — `simulation/` позволяет отработать алгоритмы без риска разбить дрон.
4. **Воспроизводимость** — любой человек с таким же железом может собрать и запустить систему по документации и схемам из `hardware/schematics/`.
5. **Открытость** — всё в одном репо, всё публично, всё версионируется через git, включая заметки из `docs/notes/`.
